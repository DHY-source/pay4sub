# 安卓收款通知监听端

本目录为原生 Java 安卓应用源代码，配合项目根目录的网页发卡服务使用。它监听个人微信、支付宝的指定格式收款通知，把候选到账事件签名后交给服务器。**通知监听并非微信/支付宝官方支付回调，不能独立证明资金已结算。** 必须先在你自己的手机上做真实小额收款测试。

## 构建 APK

已生成可供安装测试的 [card-listener-debug.apk](output/card-listener-debug.apk)，附有 [SHA-256 校验文件](output/card-listener-debug.apk.sha256) 和 [构建报告](output/build-report.json)。它不含你的服务器地址或设备密钥，需要安装后填写。当前 APK 为 debug 签名，仅供个人临时自用；尚未在实际手机安装运行。

当前版本为 **1.0.2（versionCode 3）**。请先确认服务器已应用上一版收款修复，再覆盖安装新版 APK；本次构建继续复用原 debug 签名密钥，并校验新旧证书相同，因此无需为了升级卸载或清除应用数据。不要删除原手机的配置和待上报队列。所有成功回执（包括 duplicate）仍要求对应当前事件 ID，旧服务器返回另一个事件的 ID 时会保留通知重试，避免误吞独立付款。

## 手机配置

1. 先部署服务器并取得 HTTPS 域名，在服务器本地查看安装脚本生成的 DEVICE_TOKEN。应用只接受 HTTPS 网站根地址与 32–256 位十六进制设备密钥。不要把密钥发给买家。
2. 安装 APK，进入“连接设置”页，填写网站根地址（例如 https://cards.example.com）和设备密钥，点击“保存并检查连接”。设备 ID 自动生成，可用于识别这台手机。
3. 点击“运行状态”页的“通知使用权”，或“使用帮助”页的“打开通知设置”，允许本应用访问通知。部分系统对侧载应用会限制此开关，需要先在应用信息页面允许受限设置；具体路径以手机系统为准。
4. 微信、支付宝开启收款通知和通知内容显示。先在网页后台使用**人工确认模式**，通过真实小额付款验证能产生正确的待核查记录，核对渠道、金额、实际到账时间。
5. 确认无误后，才在网页管理后台启用自动发卡。“保存并检查连接”中的连接检查只发心跳，不伪造付款，也不会触发发卡。
6. 保持手机联网、充电和自动时间，按手机厂商设置允许后台运行、自启动及不限制电量，必要时锁定最近任务。重启后打开本应用，确认监听已连接、网页后台设备在线。

系统的“通知使用权”本身覆盖多种通知；本应用代码只处理微信、支付宝包名且符合模板的收款通知，其他通知不保存、不上传。不请求联系人、短信、无障碍或相册权限。应用屏幕禁止截图和后台预览，以减少设备密钥泄露。

## 识别范围与已知限制

| 应用包名 | 标题要求 | 正文示例 |
|---|---|---|
| com.tencent.mm | 精确为 微信支付 | 微信支付收款10.00元 |
| com.eg.android.AlipayGphone | 支付宝 / 收款通知 / 支付宝收款 / 支付宝到账通知 | 你已成功收款10.00元、支付宝收款10.00元、支付宝成功收款10.00元、成功收款10.00元 |

正文必须完整匹配收款模板，可有金额两侧空格、￥/¥ 符号、末尾一个 。/！/!。金额使用整数分，范围 0.01–10,000.00 元。不接受额外句子、转账待确认、红包、退款、付款、聊天前缀或多条通知摘要。**不同微信/支付宝版本、手机厂商和通知设置可能改变标题/正文，当前模板不是对所有版本的兼容承诺。** 无法识别时不会放宽为任意金额匹配；请在实际收款记录中人工核账，确认真实通知样本后同步修改手机 ReceiptParser.java 与服务器的校验规则并重新测试。

即使包名正确，某些聊天内容也可能模仿收款通知，联系人名称也可能被伪装。专用收款账号尽量不用于聊天；不要把本方案用于高价值或无法承担误发风险的交易。签名只认证“配置了密钥的手机上报了这些字节”，不是支付平台对交易的认证。

手机不保证始终存活：系统可能停用监听、杀进程、隐藏收款通知，微信/支付宝在前台时也可能不显示系统通知。本应用没有强行常驻或绕过系统限制；每约 45 秒尝试报告监听心跳，服务器根据心跳决定是否允许自动接单。网络重连时不会主动扫描旧通知作为新收款。

固定金额无法携带订单号；由服务器实施同渠道同金额互斥、成交冷却、取消/过期锁定和人工核查。线下同额收款、晚到通知或重复通知仍可能产生歧义，请结合真实账单处理。

## 上报与重试

- 收款事件：POST /api/device/events，字段详见 [API.md](../API.md)。
- 心跳：POST /api/device/heartbeat，包含设备 ID 和真实的监听连接状态。
- X-Device-Timestamp 为请求时 Unix 秒；X-Device-Signature 为 HMAC-SHA256(DEVICE_TOKEN, timestamp + '.' + 原始 UTF-8 JSON) 的小写十六进制。设备密钥按 UTF-8 文本使用，不先解码为十六进制字节。
- TLS 使用系统证书与主机名校验，禁止明文 HTTP，禁止自动跟随重定向。手机需要能够验证服务器证书。
- 本地 SQLite 队列先持久保存匹配到的事件；请求重试保持原始事件 ID、发生时间和 JSON 正文。任何正数 notification.when 都保留为原始发生时间；仅缺失此时间时才用系统通知发布时刻。旧时间或未来时间绝不会被替换为当前时间“修复”。新请求会重新生成时间头与签名。
- 只有服务器返回 HTTP 200、ok: true、event_id 与待上报通知完全一致，以及 delivered / review / duplicate 回执时才会移出队列；其他事件 ID 或 HTTP 200 的 HTML 页面不会被当作成功。
- 每条上传前按单调时钟检查是否需要刷新 45 秒心跳，不会等整批 20 条完成。仅确认成功的心跳更新缓存时间；心跳失败会暂停本轮上传并保留队列。服务器地址、设备密钥或监听连接状态变化时，先重新报告心跳再继续上传。
- 网络失败按 15 秒起步指数退避，最长 30 分钟；4xx（429 除外）每 30 分钟重试，错误显示在应用中，可检查密钥/系统时间后手动重试。
- 成功接收后删除手机队列中的通知正文，保留去重 ID 90 天。队列最多 2,000 条待上报记录；达到上限会显示错误，必须联网处理并人工核账。
- 更改服务器地址前必须处理待上报记录；旧地址队列不会发送给新地址。清除应用数据或卸载会删除队列，不能作为重试方法。
- 超过服务器自动发卡时效的事件只供人工核查，不会因重新联网被伪装成新到账。

## 排查顺序

1. “监听未连接”：检查通知使用权、电池/后台设置；关闭再开启通知使用权，然后回到应用确认状态。
2. “HTTP 401”：核对服务器设备密钥，开启手机自动时间。
3. 网络或证书错误：确认网站根地址正确、域名解析和 HTTPS 证书有效，且手机可访问。不要关闭证书校验。
4. 心跳正常却无收款事件：真实付款后检查手机是否显示完整收款通知；先核对真实账单，再检查标题与正文是否符合上表。
5. 事件已接收但未发卡：查看网页后台待核查原因，确认真实到账后处理。
